## Project Overview

The main goal was to gain hands-on networking experience, while improving the security and visibility of my network through VLAN segmentation, DNS filtering, monitoring tools, and more.

## Problems Identified

- **Dependence on ISP hardware**

  Like many home networks, my existing network relied on the ISP's all-in-one (modem, router, firewall, switch, and wireless access point). These ISP solutions are simple, but very limited in terms of security features, visbility, and control.

- **No separation of devices**

  The previous hardware had no way of segmenting the network, which would reduce impact in the event of device compromise. Notably, unpatched systems and IoT devices such as smart home appliances, are at higher risk. Without separation, an attacker could use these vulnerable devices to pivot to other devices, or attempt to access the router's dashboard for more control.

- **Limited visibility**

  Very little insight into network activity for troubleshooting and monitoring.

## Designing the Solution

### OS & Hardware

I chose OPNsense over pfSense because the user interface felt much more intuitive to me, though, I eventually virtualized pfSense as a VM in my home lab to gain experience using both.

I chose a reliable and power-efficient mini PC to run OPNsense as my router/firewall. My architecture includes a managed switch that offers more ports (since my box only has 2), a wireless access point (one that is VLAN capable), and another mini PC to use as a server for homelabbing later on.

### Firewall Rules

Since the OPNsense firewall is deny-by-default, rules must be created for network functionality. Most of my VLAN firewall rules follow a similar pattern. I created an alias to allow access to core service ports such as DNS and NTP. I created another alias to block (and log) access to private network ranges (RFC1918), which will keep VLANs isolated unless explicitly allowed to communicate. At the very bottom, I have a rule that allows access to anything. Since firewall rules are processed from top-to-bottom, users are only allowed to access Internet services&mdash;not private networks.

Note: For enterprise networks, it would be best to apply the principle of least privilege, allowing specific services such as HTTPS and HTTP instead of a broad allow. For a home network with gaming, IoT, etc., I prioritized functionality over granular control.

### DNS

I configured Quad9, a reputable non-profit, as my upstream DNS resolver that blocks access to known malicious sites. This is an effective way of reducing the risk of phishing attempts.

For an additional layer of security and privacy, I configured my local Unbound DNS resolver to use Hagezi DNS Blocklists, which blocks trackers, ads, and malware. Through Unbound reporting, I gain insight into when my devices are attempting to send collected tracking data to various companies:

### Add-ons for Visibility & Security

Once OPNsense was up and running with core network services, I configured various add-ons to improve security and understanding of my network:

1. **ntopng**

- Network traffic monitoring for troubleshooting and insight.
- Answers questions like: Who are my devices talking to? Where are they communicating? How much data is being sent?

2. **CrowdSec**

- Uses community threat intel and firewall logs to detect suspicious behavior.
- Automatically bans repeated malicious connection attempts and scans.
- Note: I replaced Suricata IDS with CrowdSec for my network because it's lighter weight and my attack surface is lower without exposed ports.

3. **Spamhaus DROP**

- Additional layer of IP blocking to stop the "worst of the worst" traffic.
- Since OPNsense is deny-by-default, I configured it to only block traffic going out of the network in case a device is hacked.
